# ビルド化(Vite/esbuild)に関する決定事項メモ

対象: iOSアプリ(Capacitor)の起動速度改善のためのビルド化作業。
GitHub Pages配信用の`index.html`本体は対象外(後述)。

## 背景

外部レビューでの指摘:
- `vendor/babel.min.js`が2.87MB(gzip後604KB)あり、起動のたびに`Babel.transform()`で約3,500行のJSXを変換していた
- 実測(デスクトップ、高速CPU): `Babel.transform()`単体で160〜200ms。実機のiPhone(特に旧機種)ではこれより数倍かかる可能性が高い
- `eval()`を使う構成のため、CSPを`unsafe-eval`なしまで厳格化できない
- App Store審査そのものをブロックする要因ではないが(起動速度・CSP・審査時の説明のしやすさの観点で)不利

## 決定事項

### 1. Vite全面移行ではなく、iOSビルド(`www/`)だけをスコープにした

このリポジトリの`index.html`は「ビルド不要で直接編集できる」ことを設計原則にしている(CLAUDE.md参照)。もともとclaude.aiのArtifactとして作られた経緯もあり、GitHub Pages配信用の`index.html`をビルド成果物にしてしまうと、その原則が崩れる。

そのため:
- **GitHub Pages版(`index.html`)は無変更。** 今まで通りランタイムBabelで動く。zero-buildのまま
- **Capacitor(`www/`)側だけ**、`npm run sync-www`実行時に事前ビルドする方式にした

### 2. Babel(`@babel/core`)ではなくesbuildを採用

- 依存が軽い(単一バイナリ、`@babel/core`+プラグイン一式より小さい)
- JSX→`React.createElement`のclassic変換を明示的に指定でき、既存コード(グローバルの`React`/`ReactDOM`を使うUMD構成)とそのまま噛み合う
- 変換速度が速く、`npm run sync-www`の実行コストが問題にならない

### 3. 出力の構成

`scripts/sync-www.js`が以下を行う:
1. `index.html`から`<script type="text/plain" id="appsrc">`のJSXを取り出す
2. esbuildで事前トランスパイル(`jsx: "transform"`, `target: "es2019"` — `??`/`?.`等のES2020構文を下位互換のため変換)
3. `www/app.bundle.js`として書き出す
4. `www/index.html`の起動スクリプトを、ライブラリを順に読み込む`<script src>`列 + `<script src="app.bundle.js">`だけの単純な形に差し替え(Babel読み込み・`Babel.transform()`・`eval()`はすべて無し)
5. `vendor/babel.min.js`(2.87MB)は`www/vendor/`にコピーしない

### 2. iOS版の永続化をCapacitor Preferences(UserDefaults)からSQLiteへ移行

数年分のトレーニング履歴を1個のJSON文字列としてUserDefaultsへ毎回丸ごと書き直す設計は、
性能・破損・保存失敗のリスクがあったため。採用ライブラリは`@capacitor-community/sqlite@^6.0.2`

- `workouts`/`workout_exercises`/`sets`のみ正規化。`settings`/`custom_exercises`はキー1行=JSON文字列1個
  (形の決まっていない小さな設定値をカラム分割すると、フィールド追加のたびにDDL変更が要るため)
- 旧Preferencesデータからの移行は1回きり・1トランザクション・失敗しても次回起動時に再試行可能
- `workouts`配列への参照が変わっていない保存(プロフィール編集など)はworkouts系テーブルに触れない
  最適化(UserDefaults時代の「小さな変更で履歴全体を書き直す」問題を繰り返さないため)
- Web版は変更なし(引き続きlocalStorage)。`src/domain/storage.js`が`workout-log-v1`キーだけを
  ネイティブ+SQLiteプラグインが使える環境でSQLite経由にすり替える

### 3. Xcodeシミュレータでの実機相当検証で見つけたバグを修正

`CapacitorSQLite.query()`の戻り値(`values`配列)は、**先頭要素だけが`{"ios_columns":[列名,...]}`
という特殊なメタデータ行**という仕様だった。Swiftソースの型だけを見て「先頭行も含めて全部が
`{列名:値}`の行オブジェクト」と誤読して実装し、実機で「settings行のJSON.parseに失敗」という
バグを引き起こした。`capacitorSqliteDriver.js`に`normalizeRows()`を追加して修正。
詳細は[DATA_MIGRATION.md](../DATA_MIGRATION.md)の「実機検証で見つけた不具合」を参照。

同じ検証で、旧バージョンからの更新(Preferencesに旧データがある状態からの起動)・二重移行防止・
前回記録の表示・バックアップ書き出しが実機で正しく動作することも確認済み。

### 4. その他のP0対応

- `support.html`新規作成、Support URLをmailtoから`support.html`のURLに変更

- YouTube検索機能とprivacy.html/APPSTORE.mdの「外部通信なし」表記の矛盾を解消

# 2026-08-19: ユーザー要望6件の実装

このセクションも上記2件とは別件。ユーザーから投げ込まれた11件の改善要望を調査・検討し、
優先順位「5番(確認のみ)→9番・2番(低コスト)→6番・7番」の指示どおりに実装した。

## 決定事項

### 1. RIR未入力セットの除外(5番)は調査の結果、実装済みと判明

`saveWorkout`/`saveEditWorkout`のフィルタ条件(`reps>0 && (warmup || RIR入力済み)`)が
既に要望どおりに動いていた。実機で3セット入力(RIR入力1件・未入力2件)して保存し、
履歴に1セットのみ残ることを確認。**コード変更なし。**

### 2. 部位名「胸」→「大胸筋」(2番)

解剖学的に不正確な「胸」を正しい部位名に改名。`normMuscle()`に「胸/上部胸筋→大胸筋」の
正規化を追加し、既存記録のmuscle文字列が書き換わらなくても起動時に自動移行されるようにした
(過去の「背中→広背筋」と同じパターン)。これが無いと旧「胸」と新「大胸筋」が週間集計・

### 1. 8番はクローズ

Web標準から検出不可能)だったため、ユーザー判断でクローズ。保留5件の記述を更新済み。

### 2. 3番は「器具を選べる機能」ではなく「カスタム種目追加時に器具が強制的にダンベルになる不具合」の修正だった

要望原文は「記録画面で新しい種目をカスタム追加すると、強制的にダンベルになる」。当初は
「器具ごとに前回実績を別トラックとして記録したい」という新機能かと想定して調査を始めたが、
ユーザーに確認した結果、実態は不具合修正だと判明。前回実績のゴースト比較(このアプリの
中心機能)は器具に関係なく種目名だけで行う「現状維持」で良いことも確認済み。

原因は2つ:
- `customDraft`(カスタム種目追加時の下書き)の`eq`初期値が`"ダンベル"`固定で、ユーザーが
  明示的に選ばない限り常にダンベル扱いになっていた
- 記録画面の「セット間に種目を挿入」パネルには、そもそも部位・器具を選ぶセレクトUI自体が
  存在せず、常に前回選択値(初回はダンベル)を無条件に使っていた

対応: `customDraft`の`eq`初期値を空文字に変更し、下部の通常種目選択パネルのセレクトに
プレースホルダー(`settings.other`キー流用)を追加。挿入パネルにも、下部パネルと同一構成の
muscle/eqセレクトを新規追加した。

### 3. 4番は「使用中の種目を部位ごとに見出し付きで縦に並べる」形にした

現状は「部位チップを1つ選んで絞り込む」方式だったが、「全部位を見出し付きで縦に並べ、
部位チップは該当見出しへジャンプするショートカットにする」方式に変更。母集団(検索なしなら
「使用中の種目」のみ、検索時は`allExercises`全体)は既存のロジックをそのまま維持した。

### 4. reviewerの指摘で2点修正した

`reviewer`エージェントによる別文脈レビューで、実装直後には気づいていなかった2つの不整合が
見つかり、修正した:

- **器具フォールバック値の不整合**: `addExercise`内の`customExercises`登録処理が
  `eq: meta?.eq || customDraft.eq || "その他"`となっており、未選択時に文字列`"その他"`が
  保存されていた。一方、器具を選ぶ全ての`<select>`はプレースホルダーの値を空文字(`""`)で
  統一しており、`<option value="その他">`という選択肢自体が存在しない。保存値`"その他"`と
  select側のoption値`""`が食い違うため、後で設定タブからこの種目を編集しようとすると
  選択状態が壊れる(ブラウザが未一致のvalueを最初のoptionへフォールバック表示するため、
  偶然「その他」と見えることはあるが、Reactの認識としては不一致のまま)。
  `|| "その他"`を`|| ""`に修正し、保存値をプレースホルダーの実値と一致させた。
- **部位チップの母集団ズレ**: 部位チップの生成元が`allExercises`(全94種目+カスタム)のままで、
  実際に見出しとして描画される一覧(既定では「使用中の種目」のみ、母集団がずっと狭い)と
  ズレていた。結果、既定表示では大半のチップがジャンプ先の見出しを持たず無反応になっていた。
  チップの母集団を、リストと同じ`pool`(検索/使用中の絞り込み後の実データ)から算出するように
  修正し、チップとリストの`pool`計算を1つのIIFEに統合した。「未設定」グループへのジャンプ
  チップも同様に追加した。

いずれも`npm test`や目視だけでは気づきにくい種類の不整合(保存データの形とUIの想定形の
すり合わせ漏れ)で、実装者本人による自己レビューを素通りしていた。別文脈レビューの効果が
出た例として記録しておく。

# 2026-08-23: Apple Watch連携の代替として休憩タイマーをローカル通知化、収益化方針を決定

Apple Watch連携をやりたいという相談から始まったセッション。調査の結果、watchOSアプリの
新規開発ではなく、休憩タイマーのローカル通知化という形で実質的な目的を達成する方針にした。
別件で収益化方針(有料/無料)もこのセッションで決定した。

## 決定事項

### 1. Apple Watch連携はwatchOSアプリを作らず、ローカル通知で代替する

調査の結果、以下が判明した:
- **watchOSアプリはWebView技術で作れない**。SwiftUI/WatchKitによる完全な新規ネイティブ実装が
  必須で、`index.html`のコードは1行も再利用できない(Appleのエンジニアがフォーラムで明言)
- 公式の`@capacitor/watch`プラグインは実質メンテナンス停止(最新v0.1.12、peer依存が
  `@capacitor/core: ^5.0.0`でこのアプリの6系とは非互換、最終更新2024-04、公式ドキュメントは404)
- **App Group経由でのSQLite共有は不可能**。`@capacitor-community/sqlite`の実コード
  (`UtilsFile.swift`の`getFolderURL`)が許可リスト外のパスを拒否する実装になっており、
  `iosDatabaseLocation`にApp Groupコンテナを指定する手段が無い
- 一方、**ロック中のiPhoneのローカル通知はApple Watchへ自動転送される**(Apple公式)。
  Watchアプリを書かずに「手首で休憩の終わりを知る」という目的の大部分を達成できる

将来Watchアプリを作るなら、案B(今日のメニュー・前回実績の閲覧、読み取り専用)が
片方向同期で済み費用対効果が最良と判断。案C(Watch単体で記録入力)はドメインロジックが
JSとSwiftに二重化し、個人開発では保守しきれないため非推奨とした。

### 2. 休憩タイマーをローカル通知化(`@capacitor/local-notifications@6.1.3`)

休憩タイマーは`setInterval` + `AudioContext`のみで実装されており、iOSはWebViewが
バックグラウンドに入るとJSタイマーを止めるため、**アプリを閉じると経過も通知音も止まる**
という既存の不具合があった(ジムでスマホを置く実際の使い方で機能していなかった)。
ローカル通知はOS側が発火するためバックグラウンドでも確実に届く。

- **通知と通知音は排他にした**(二重通知の回避)。Capacitor iOSの通知は前面でもバナーを
  出すのが既定のため、ネイティブ+許可済みのときは分刻みの`beep()`を鳴らさず通知に一本化した
- **通知操作を`useRef`のPromiseチェーンで直列化した(実バグ対策)**。`startRest()`は
  重量/回数のonBlurから連続発火し`restStartAt`が短時間に何度も変わるため、直列化しないと
  前の実行の`cancel`が後の実行の`schedule`を追い越して消す経路が実在した(起動時、初回
  レンダーの`cancel`が下書き復元の`schedule`を後から消すケースが最悪)
- 通知許可の要求は「`restStartAt`がnull→非nullに変わったとき」だけ、セッション中1回。
  設定の`soundOn`トグル操作では要求しない(休憩中にトグルすると唐突にダイアログが出るため)
- 新しい設定項目は増やさず、既存の「インターバルの通知音」トグルに相乗りさせた
  (文言は音だけでなく通知も指す内容に更新。「サイレントスイッチがオフだと鳴らない」という
  記述もネイティブでは不正確になるため書き換えた)
- 起動時に前回の予約通知を掃除する専用effectを、タイマーeffectより宣言順で先に配置。
  セット未入力のままインターバルを開始してアプリを終了すると、アプリが存在を知らない
  通知だけが後から鳴る経路があったため

### 3. 収益化方針を決定(別件)

`MONETIZATION.md`の「案A(買い切り)推奨」という下書きを、**案B(無料ダウンロード+
記録10回まで試用+非消耗型IAP)**に変更して決定した。試用条件は暦日ベースではなく
**記録回数ベース**にした。理由: このアプリの中心機能(前回の同じ番手のセットをそのまま
見せる比較表示)は同じ分割日を2周目に回さないと発動せず、5分割だと1〜2週間かかることが
多い。暦日ベースの試用だと、多くのユーザーが中心的な価値を体験する前に試用期間が切れて
しまう。StoreKit実装そのものはこのセッションでは着手せず、Apple Developer Program登録・
Xcode署名・Archive検証といった提出の段取りを先に固めることを優先した。

# 2026-08-23(5回目): 種目ごとの「AI相談」、履歴カレンダーの常時表示

記録タブの各種目カードから、その種目の相談用プロンプトを持ってAIチャットへ飛べるようにした。
あわせて履歴タブのリスト/カレンダー切替を廃止した。

## 決定事項

### 1. プロンプトはクリップボード経由で渡す。URLのクエリには載せない

**これが今回の中心的な判断。** 「AIサイトを開いてプロンプトを直接表示」も検討したが採らなかった。
理由は3つで、重い順に:

1. **プライバシー申告が崩れる。** `privacy.html` の「これらのデータは本アプリの外部に送信される
   ことはなく」と `APPSTORE.md` の Data Not Collected の根拠説明は、記録を `?q=` に載せて
   chatgpt.com を開いた時点で成り立たなくなる。クリップボードは端末内で完結するので、
   「アプリが送信した」のではなく「ユーザーが貼り付けた」と正しく区別できる
2. **対応が一部サービスに限られる。** Claude は2025-10に `?q=` を削除(再要望も closed as
   not planned)、Copilot は無効化済み、Gemini は元から非対応。ChatGPT は動くが、
   2025-07-11 の修正でクロスサイト遷移では自動送信されず事前入力止まりになった。
   「デフォルトのAIを設定する」機能と、選んだサービスによって挙動が変わる仕様は相性が悪い
3. **公式仕様ではないので黙って壊れる。** 公式にドキュメント化されているのは Claude Code の
   `claude://code/new?q=` だけで、他は全て有志が見つけた非公式。しかも削られる理由が利便性では
   なく**プロンプトインジェクション対策**なので、復活は期待しにくい

なお **URLの長さは制約にならなかった**。当初「日本語はencodeURIComponentで1文字9文字になるので
210文字が上限」と見積もったが、これは全部が日本語の場合の最悪値。実際のプロンプト(種目1つ・
履歴3回分、189字)はエンコード後802字で、安全圏の2,048字に余裕で収まる。重量・回数・日付など
数字が大半を占めるため。**却下の理由は長さではなく上記3点。**

`window.open` による外部遷移自体は既にYouTube検索で前例があり、`tests/sync-www.test.js` の
外部通信検査も「window.openは対象外」とコメントで明示している。

### 2. YouTubeボタンを種目名の行へ移した

種目カードのボタン行は、375px幅で**追加前から既に溢れていた**(行313pxに対しボタン+gapが315px)。
そこへ「AI相談」を足すと更に窮屈になる。YouTube(67px)を種目名の行の右端へ移すことで、
ボタンを1つ増やしながら**行の高さが64px→32pxに減った**(2行→1行)。

副次的に、赤いYouTubeが操作ボタン群から離れて視線を引きすぎなくなった。YouTubeは種目に紐づく
参照リンクなので、種目名の隣にある方が意味的にも自然。

### 3. プロンプトの内容

「次にどの重量・回数で組むべきか」を判断するのに要る材料を、数値の羅列ではなく前提込みで渡す:
種目の設定(部位・器具・片手/体重込み)・体重・目標レップ数・重量の刻み・自己ベスト・
直近5回の全セット・連続回数・今日ここまで・種目メモ。

**RIRの注記(`share.rirNote`)は必須。** これが無いとAIが「余力2」を「2回しかできない」等と
誤読して逆方向の助言をする。同じ理由で、ダンベルの「片手」表記と、自己ベストが実効重量
(両手合計・体重込み)である但し書きも入れている。

### 4. 履歴のカレンダーを常時表示にした

リスト/カレンダーの切替チップを廃止。どちらか一方しか見られない作りで、切替の存在自体が
余計だった。日付タップでその日の記録に絞り込む挙動はそのまま残している。

SWが1つも登録されていない素のブラウザでも起きる**ことが分かった。`src/domain/i18n.js` を
既定キャッシュでfetchすると41,906バイト(旧)、`{cache:'reload'}` だと43,652バイト(新)という
状態になり、画面には `log.consultAi` という生キーがそのまま出ていた。
**クエリ付きURLでのリロードだけでは足りず、`<script src>` の実URLを再検証する必要がある。**

## 残っている課題

- `window.open` がポップアップブロッカーに弾かれたときの経路が無い(戻り値を見ていない)。
  クリップボードには入っているので致命的ではないが、ユーザーには失敗に見える
- 各AIサービスのチャット画面が、実機のiOSでUniversal Link経由ネイティブアプリに飛ぶかは未確認
  (Capacitorは `UIApplication.shared.open()` に委ねるので飛ぶ見込み。実機が要る)
- `exerciseToText` は `#appsrc` 内でstate依存のためテストが無い。1のような単位バグは
  `src/domain/` の純粋関数にしていれば1行のテストで捕まる種類だった
