# 可動域係数(rom)と体重係数(bw)の根拠

種目マスター(`index.html` の `EXERCISE_DB`)が持つ2つの係数について、**どう導出したか**を残す。
値だけを残すと「なぜ0.3なのか」に後から答えられなくなる。ここが以前まさに弱点だった
(romは該当8種目が一律0.5で、測定でも計算でもない当て推量だった)。

**これらはユーザーが⚙から変更できる初期値である。** 目指しているのは「出典のある真実」ではなく
「ユーザーが直す前の、実態に近い出発点」。したがって推定であること自体は許容し、
代わりに前提と計算過程を書いて検証可能にしている。

---

## 可動域係数(rom)

### 導出式

```
rom = clamp(荷重が動く距離cm ÷ 40cm, 0.2, 1.0)   → 0.05刻みに丸め
```

- **40cm** = 標準的なプレス/スクワットで荷重が動く距離。ここを1.0の基準にした
- **上限1.0(減点のみ)**。可動域の長い種目を加点はしない。この係数の目的は
  「重量の割に可動域が短い種目が集計を支配するのを防ぐ」ことであって、仕事量の計算ではない
- 集計ボリュームにのみ効く。推定1RM・PR・メニュー判定には影響しない

### 適用した種目

| 種目 | 距離 | rom | 距離の見積もり |
|---|---|---|---|
| バーベルシュラッグ | 10cm | 0.30 | 肩甲骨挙上のみ。腕・肘は動かない |
| ダンベルシュラッグ | 12cm | 0.30 | 同上(系列で統一) |
| ケーブルシュラッグ | 10cm | 0.30 | 同上(系列で統一) |
| スタンディングカーフレイズ | 14cm | 0.30 | 足関節底屈のみ。踵の上下(系列で統一) |
| シーテッドカーフレイズ | 12cm | 0.30 | 同上 |
| レッグプレスカーフレイズ | 12cm | 0.30 | 同上 |
| リストカール | 15cm | 0.30 | 手掌の回転半径約10cm × 手関節屈曲約85度(系列で統一) |
| リバースリストカール | 12cm | 0.30 | 伸展可動域は屈曲より狭い(約70度) |
| ラックプル | 25cm | 0.65 | 膝上スタート。デッドリフトの上半分のみ |
| ヒップスラスト | 28cm | 0.70 | 床近く→股関節伸展位までのバー鉛直移動 |
| プッシュアップ | 25cm | 0.65 | 足支点の回転。胸は約35cm動くが重心(腰寄り)の移動は約7割 |
| インバーテッドロウ | 30cm | 0.75 | 足支点の回転。胸は約40cm動くが重心移動は7〜8割 |
| クランチ | 20cm | 0.50 | 脊柱屈曲のみ。上部体幹重心の移動。股関節は動かさない |
| ケーブルクランチ | 30cm | 0.75 | 膝立ちで屈曲角を大きく取れる |
| アブドミナルマシン | 30cm | 0.75 | パッド半径約40cm × 体幹屈曲約45度 |

系列(器具違いで動きが同じ組)は**必ず同値に揃える**。推定元のcmは10/12/14とブレるが、
これはAI推定の精度より細かい差で、意味のある差ではない。`tests/exerciseCoefficients.test.js`
が割れを機械的に検出する。

### 意図的に適用しなかった種目

式をそのまま当てると20種目が変わるが、以下は**入れていない**。

| 種目 | 式の値 | 見送った理由 |
|---|---|---|
| バーベルベントオーバーロウ / Tバーロウ | 0.90 | 35cm vs 40cmは推定誤差の範囲。ボリュームが膨らんでいる実害も無い |
| バックエクステンション / ヒップアブダクション / ベンチディップス | 0.90 | 同上 |

**判断の基準**: 「短い可動域 × 高い実効負荷でボリュームが不当に膨らむもの」だけに当てる。
0.9前後の減点は意味のあるシグナルにならず、ノイズを持ち込むだけになる。

### 距離では表現できない種目

- **ファーマーズウォーク**: 等尺性で荷重が上下しないため、この式が成立しない。
  距離0にすると係数0.2で不当に減点されるので、**romを付けず1.0のまま**にしている。
  そもそも `reps` が歩数か秒数かで意味が変わるので、ボリューム集計自体の妥当性が別問題。

### この推定の限界

- **一次情報は無い。** 94種目の荷重移動距離を列挙した公表資料・査読論文は確認できなかった。
  上記はすべて体節長(身長170cm前後)と関節可動域からの幾何推定である
- 弧長で測ると**単関節種目のほうが長く出る**(フロントレイズ95cm、サイドレイズ85cm、
  カール70cm)。上限1.0で頭打ちなので実害は無いが、「サイドレイズはベンチプレスより
  仕事量が多い」という直感に反する結果になる。回転種目に弧長を当てるのは概念的に無理があり、
  **この式は「短い種目を見つける」用途にのみ使える**と理解しておくこと
- 体格依存が大きい項目(懸垂、ディップス、腕の弧長、ステップアップの台高)は
  170cm前提を外すと±20%程度ぶれる

## 体重係数(bw)

自重種目の実効重量は `体重 × bw + 加重` で計算する(`src/domain/oneRm.js` の `effWeight`)。

すべて**可動域の中間位**の値。プッシュアップのように上端と下端で値が変わる種目があるため、
位置を固定しないと数字が揺れる。

### 実測研究が見つかったもの

| 種目 | bw | 出典 |
|---|---|---|
| プッシュアップ | 0.70 | Ebben et al., JSCR 25(10):2891-2894, 2011(標準フォームで65%、男性で64-72%)。Suprak et al., JSCR 2011 が上端/下端の差を報告し、下端は70-75%。中間位としてその中間を採用 |
| インバーテッドロウ | 0.65 | Vural et al., PLoS ONE 2023(PMC10516423)。TRXで等尺性69.5%・等張性73.4%BW。これはほぼ水平の体幹での値で、バー使用時は体幹が起きるためcos補正して0.65 |
| ノルディックハムカール | 0.85 | Jeanguyot et al., Biology of Sport 2023(PMC10588571)。足首実測で膝屈筋の最大偏心力が両脚0.86-0.96BW。独立に立てたレバーモデル(0.91)とも一致 |

**注意**: Ebben / Suprak は抄録・書誌のみ一次確認で、個別数値は二次情報経由。

### レバー計算による推定(実測なし)

| 種目 | bw | 計算 |
|---|---|---|
| ベンチディップス | 0.75 | かかと支点の静的モーメント。脚(0.32BW、重心はかかと-股関節の6割)とHAT(0.68BW、重心はほぼ手の真上)の合成 → 約0.78。膝を曲げて足裏を床につける形なら約0.70 |
| バックエクステンション | 0.40 | 45度台、中間位=水平から約57度。HAT 0.68 × cos57° ≒ 0.37。ローマンチェア(水平台、中間位45度)なら0.68 × cos45° ≒ 0.48 |
| クランチ | 0.35 | 持ち上がるのは頭頸部(0.08)+両腕(0.10)+胸郭(0.22)= 約0.40。中間位のモーメント補正で0.35 |
| アブローラー | 0.45 | 膝コロ。膝支点で膝上0.88BW・重心は膝から約0.63m、手の接地は約1.3m → 0.88×(0.63/1.3) ≒ 0.43。立ちコロなら0.6-0.7 |
| ハンギングレッグレイズ | 0.30 | 両脚 0.32BW × 中間位補正、上端の骨盤の巻き上げ分を加算。**ぶら下がる体重は握力・広背筋にかかるもので腹筋の負荷ではない** |
| レッグレイズ | 0.25 | 両脚 2×0.161 = 0.32BW × cos45° ≒ 0.23 |
| ディップス | 0.95(据え置き) | 全体重が手で支持される。腕に対して動かない前腕+手(体重の4-5%)を差し引いた見積もり |
| 懸垂 | 1.00(据え置き) | 力学的には0.95-0.96が妥当だが、加重懸垂は慣習的に「体重+加重」で語られ、ヘルプ文言もそれを前提にしているため1.0を維持 |

セグメント質量比(HAT 0.68、片脚 0.161、前腕+手 0.022)は広く引用される値をモデルの前提に
置いたもので、**一次出典は確認できていない**(Winter の Dempster表 / Plagenhoef et al. 1983 が
候補だが、PDFが取得できなかった)。

### 意図的に係数を付けなかった種目

| 種目 | 理由 |
|---|---|
| ブルガリアンスクワット / ランジ / ステップアップ | **`db: true` なので `effWeight` が体重まで2倍にする**(`if (isDb) w = w * 2`)。係数を入れるには先に `effWeight` の改修が要る。力学的には前脚が体重の8割強を負担しており(Helme らの RFESS 前足84.36%)、根拠自体はある |
| アシスト懸垂 | 実効負荷は「体重 − 補助」だが、`体重 × 係数 + 重量` の式では負の重量を入れないと表現できず、「補助を増やすほど記録上の重量が増える」逆転が起きる。セットの `assisted` フラグで扱う現行方針のほうが破綻が少ない |
| ケーブルクランチ / アブドミナルマシン | 体幹の自重モーメントは寄与するが、スタック重量と二重計上になる |

`db: true` と `bw` の併用は `tests/exerciseCoefficients.test.js` が禁止している。
**ただし縛れているのは種目マスターの値だけ**で、ランタイムでは同じ状態を作れる:
記録画面の⚙の「自重種目」チェックは種目の `db` を見ておらず、ダンベルシュラッグ
(`db: true`)でONにすると `bwFactor 0.7` × `isDb true` になり、実効重量が
`(体重×0.7 + 加重) × 2` になる。**この穴は未修正**(今回の変更が持ち込んだものではない)。
塞ぐなら `effWeight` の改修か、UI側で排他にする必要がある。

## 値の優先順位

```
ユーザーの調整 > カスタム種目の定義 > 種目マスターの既定値
```

解決は `src/domain/coefficients.js` の `resolveCoefficients(name, lookup)`。
`lookup` には **`findExercise` を渡す**(`allExercises` = 内蔵 + カスタム に
`exerciseOverrides` をマージ済みの索引)。

**記録側に焼き込まれた値は優先順位に入らない。** ここはv102で変えた。`saveWorkout` は
毎回 `rom`/`bwFactor` を記録に書き込むが、それは「その日の計算に使った値」のスナップショット
であって、ユーザーがそう決めたという意思表示ではない。以前はここから読み戻していたため、
**一度でも記録した種目はマスターの既定値を更新しても永久に古い値のまま回り続けていた**
(しかも `saveWorkout` がまた書き戻すので自己増殖する)。

### 直すときに踏んだ落とし穴(3つとも実際にやった)

1. **`lastConfig` だけ直しても効かない。** 「今日のメニュー」は `buildMenuItem` が
   `prevEx.rom ?? cfg.rom` と記録を直読みしており、`saveWorkout` が必ず数値を書くため
   `??` は絶対にフォールバックしない。しかもv101で「今日のメニュー」は前回の実記録を
   最優先にしたので、**継続ユーザーが毎日通るのはこちら**。両方直さないと、
   手で種目を足したときとメニューから始めたときで同じ種目に別の係数が付く
2. **`dbLookup` はカスタム種目を見ない**(`DB_BY_NAME` + `EXERCISE_OVERRIDES` のみ)。
   ここを索引に使うと自重のカスタム種目が `bwFactor: 0` になり、実効重量もボリュームも
   推定1RMも0のまま記録される。`findExercise` を使うこと
3. **⚙が無編集でも上書きを書くと、潰したはずのバグをUI経由で再生産する。**
   フィールドを触って他所をタップしただけで `exerciseOverrides` が作られ、以後その種目に
   マスターの更新が永久に届かなくなる。**値が変わったときだけ書く**

記録画面の⚙での調整は、そのままだと翌日に残らないので `updateCustomExercise` で
`exerciseOverrides`(カスタム種目なら `customExercises` の実体)にも書いている。
「自重種目」チェックボックスも ON/OFF の両方を書く。書かないと OFF が翌日に残らず、
マスターに `bw` を持つ種目では 0.7 が復活して重量欄の意味が「加重」に戻る。

### 既知の穴(未修正)

- **`resolveRom` のフォールバックだけは `dbLookup` のまま**で、カスタム種目を見ない。
  `rom` フィールドを持たない古いバックアップを復元したカスタム種目は、集計時にカスタム側の
  `rom` が無視されて1.0で数えられる。`resolveRom` はコンポーネント外の定数で
  `customExercises` に触れないため、直すなら `volumeDeps` 経由の注入が要る
- **種目マスターから消した種目は係数を失う。** 記録側から読み戻さなくなったので、
  自作の自重種目を設定タブで削除すると、翌日「今日のメニュー」にはその種目が並ぶのに
  (`buildMenuItem` は `workouts` から拾うので削除の影響を受けない)`bwFactor: 0` になり、
  ボリュームも推定1RMも実質0のまま記録される。警告は出ない
- **記録画面の⚙は「今日の記録の設定」から「種目のグローバル設定」に意味が変わった**が、
  UIの見た目は変わっていない。今日だけ試すつもりの調整が将来の既定値になる
- **カスタム自重種目で `bw: 0` になると復帰が難しい。** 内蔵種目は「元に戻す」ボタンが出るが、
  カスタム種目は実体を書き換えるためボタンが出ず、`e.bw > 0` の条件で入力欄自体も消える
  (記録画面の⚙のチェックボックスなら0.7で復帰できる)

## 過去の記録への影響

**基本的に壊れない。** `src/domain/volume.js` は記録側の `rom`/`bwFactor` を読み、
`saveWorkout` がそれを保存時に焼き込んでいるため、過去の集計は変わらない。

**ただし `rom` には例外がある。** `resolveRom` は保存値が無い(`undefined`)場合に
現在のマスター値へフォールバックする:

```js
const resolveRom = (name, storedRom) => {
  const v = parseFloat(storedRom);
  if (!isNaN(v) && v > 0) return v;
  return dbLookup(name)?.rom ?? 1.0;   // ← ここ
};
```

そのため **`rom` フィールドを持たない古い記録は、過去のボリュームが遡って変わる**
(週間の部位別集計・`compareBase`・`sameSplitSessions`・履歴一覧はすべて保存値ではなく
再計算するため)。該当するのは `rom` が無かった時代のバックアップJSONを復元した場合など。
`bwFactor` は `setVolume` 側でフォールバックしないので遡らない。**romだけが非対称**。

### 上部バーのゲージへの副作用

**上部バーのボリュームゲージは「今日 vs 同じ分割日の直近3回平均」で比較する**ため、
係数を下げた種目をやっていた人は、実力が変わっていないのに数週間「基準に届いていない」と
表示される。データは壊れないので許容とした(過去分を再計算すると「過去の記録は当時の
設定のまま残る」という既存の約束と衝突する)。

### 見た目の変化

`ROM×0.65` のようなバッジが記録行に出るのは `resolveRom(...) < 1` のときなので、
**新たに7種目(プッシュアップ / インバーテッドロウ / ラックプル / ヒップスラスト /
クランチ / ケーブルクランチ / アブドミナルマシン)でバッジが表示される。**
ユーザーから見て最初に目に入る変化はここ。

### bwとromを両方下げた種目の複合効果

表を別々に見ると読み取れないので、掛け合わせた結果を書いておく(体重70kg)。

| 種目 | bw | rom | 集計ボリュームの変化 |
|---|---|---|---|
| クランチ | 0.4 → 0.35 | 1.0 → 0.5 | 約 **-56%**(560 → 245kg / 20回) |
| プッシュアップ | 0.65 → 0.70 | 1.0 → 0.65 | 約 **-30%**(910 → 637kg / 20回) |
| インバーテッドロウ | 0.7 → 0.65 | 1.0 → 0.75 | 約 **-30%**(735 → 512kg / 15回) |

プッシュアップは **bwを上げたのにボリュームは減る**。表だけ見ると読み取れないので注意。

## テストで縛っているもの

`tests/coefficients.test.js`(解決ロジック単体):

- ユーザーの上書き > カスタム種目の定義 > マスター既定値 の順になる
- **カスタム種目の体重係数が失われない**(落とし穴2の再発防止)

`tests/exerciseCoefficients.test.js` の「係数の配線(#appsrc)」(**呼び出し側**):

実際に事故ったのは解決ロジックではなく配線のほうで、`npm test` は `index.html` を実行しない
ため単体テストだけでは全部緑のまま素通りする。`#appsrc` をテキストとして検査して縛っている
(コメント行は落としてから見る。落とさないと罠を説明したコメント自体に反応する)。

- `記録側の値 ?? 設定側の値` の形が実装に無い(落とし穴1)
- 索引に `findExercise` を渡している(落とし穴2)
- 上書きを書く確定経路がすべて「値が変わったときだけ」になっている(落とし穴3)

3つとも、故意に元の書き方へ戻して検出されることを確認済み。

`tests/exerciseCoefficients.test.js`(マスターの値そのもの):

- 同じ動きの系列(シュラッグ3種・カーフレイズ3種・リストカール2種)でromが割れていない
- romが0.2〜1.0(減点のみ。1.0超えの加点をしない)
- `db: true` の種目に `bw` を付けていない(`effWeight` の二重計上防止)
- bwが0より大きく1.0以下
- 自重種目の大小関係(腕立て < ディップス ≦ 懸垂、ベンチディップス < ディップス、
  インバーテッドロウ < 懸垂)

いずれも故意に壊して検出することを確認済み。
