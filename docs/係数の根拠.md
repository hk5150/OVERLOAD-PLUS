# 可動域係数(rom)と体重係数(bw)の根拠

種目マスター(`index.html` の `EXERCISE_DB`)が持つ2つの係数について、**どう導出したか**を残す。
値だけを残すと「なぜ0.3なのか」に後から答えられなくなる。ここが以前まさに弱点だった
(romは該当8種目が一律0.5で、測定でも計算でもない当て推量だった)。

**これらはユーザーが⚙から変更できる初期値である。** 目指しているのは「出典のある真実」ではなく
「ユーザーが直す前の、実態に近い出発点」。したがって推定であること自体は許容し、
代わりに前提と計算過程を書いて検証可能にしている。

## 可動域係数(rom)

### 導出式

```
rom = clamp(荷重が動く距離cm ÷ 40cm, 0.2, 1.0)   → 0.05刻みに丸め
```

- **距離は荷重の鉛直移動**で測る(マシン・ケーブルはスタックの移動)。重力に逆らう仕事は
  m·g·Δh で経路によらないため。2026-10 までは「弧長」と書いていたが誤り(下の「この推定の限界」)
- **40cm** = 標準的なプレス/スクワットで荷重が動く距離。ここを1.0の基準にした。
  実測と矛盾しない: ベンチプレスのフル可動域は平均43.4cm(Martínez-Cava et al., JSSM 2019)、
  重いバックスクワットは52〜56cm、デッドリフトは身長の26.0%(170cmで約44cm)、
  スモウは21.2%(約36cm)(Escamilla。Frontiers 2025 経由)
- **上限1.0(減点のみ)**。可動域の長い種目を加点はしない。この係数の目的は
  「重量の割に可動域が短い種目が集計を支配するのを防ぐ」ことであって、仕事量の計算ではない
- 集計ボリュームにのみ効く。推定1RM・PR・メニュー判定には影響しない

### 意図的に適用しなかった種目

式をそのまま当てると20種目が変わるが、以下は**入れていない**。

| 種目 | 式の値 | 見送った理由 |
|---|---|---|
| バーベルベントオーバーロウ / Tバーロウ | 0.90 | 35cm vs 40cmは推定誤差の範囲。ボリュームが膨らんでいる実害も無い |
| バックエクステンション / ヒップアブダクション / ベンチディップス | 0.90 | 同上 |
| プッシュアップ / インバーテッドロウ | 0.90 / 1.0 | 下の「レバー比の二重計上」 |
| ディップス | 0.8〜0.85 | 肩の降下は約30〜33cm(式で0.75〜0.83)。推定の幅が基準の0.8をまたぐので、当てない側に倒した(2026-10) |

**判断の基準**(2026-10 に明文化): **式の値が0.8以下なら負荷の大小によらず当てる。
0.85〜0.95は当てない。** 以前は「短い可動域 × 高い実効負荷で膨らむものだけ」と書いていたが、
実際には実効負荷の小さいリストカールやクランチにも当てていて、文面と運用がずれていた。
0.8 で線を引くと、上の表の既存値はすべて説明がつく。
0.9前後の減点は意味のあるシグナルにならず、ノイズを持ち込むだけになる。

### レバー比の二重計上(プッシュアップ・インバーテッドロウから rom を外した、2026-10)

2026-10 まで、プッシュアップは rom 0.65、インバーテッドロウは rom 0.75 を持っていた
(「胸は約35cm動くが、重心の移動はその約7割」という見積もり)。これは誤りだった。

両種目の bw(0.70 / 0.65)は**手の下で測った力**で、すでにレバー比(体重のうち手が受け持つ割合)を
含んでいる。足を支点としたモーメントの釣り合いから

```
手の力 × 胸の移動量 = 体重 × 重心の移動量
```

が成り立つので、手の力(bw)と組むべき距離は**胸の移動量**(35cm / 40cm)になる。
式に入れると 0.875 / 1.0 で、上の基準ではどちらも当てない。旧値は bw と rom の両方に
レバー比を掛けていて、プッシュアップは 0.7 × 0.65 = 0.455(物理的には約0.61)と、
**約25%少なく**数えていた。

- ベンチディップス(bw 0.75、rom 1.0)はレバー比を bw 側だけに入れていて、正しい
- クランチ(bw 0.35、rom 0.5)は「持ち上がる質量 × その重心の移動」なので二重計上ではない
- 過去の記録は保存時の rom(0.65 / 0.75)を焼き込んでいるので変わらない。新しい記録から
  ボリュームが約+54% / +33% になり、`ROM×` のバッジが消える

**rom で直してはいけないもの**: レッグプレスやハックスクワットの重量が大きく見えるのは、
可動域ではなく荷重の向き(45°のスレッドでは重力成分が約0.71)のせい。ランドマインや
ケーブルのプーリー比も同じで、**実効重量の問題**。rom で代用すると「可動域が短い」という
誤ったバッジが出る。扱うなら別の係数を設けること。

### 距離では表現できない種目

- **ファーマーズウォーク**: 等尺性で荷重が上下しないため、この式が成立しない。
  距離0にすると係数0.2で不当に減点されるので、**romを付けず1.0のまま**にしている。
  そもそも `reps` が歩数か秒数かで意味が変わるので、ボリューム集計自体の妥当性が別問題。

### この推定の限界

- **種目ごとの一次情報はほぼ無い。** 実測があるのはベンチ・スクワット・デッドリフトだけで、
  ほかの表の値は体節長(身長170cm前後)と関節可動域からの幾何推定である
- 以前は弧長で測っていて、単関節種目のほうが長く出ていた(フロントレイズ95cm、サイドレイズ85cm)。
  鉛直移動で測り直すとサイドレイズ・カールとも約55〜60cmで、結論(1.0)は変わらない
- **rom が必要な理由は実測で裏づけられる。** Martínez-Cava 2019 では、ベンチの1/3可動域(14.9cm)で
  1RMが1.37倍になる一方、距離は0.34倍。重量×回数で数えるとフル可動域より37%多く見えるのに、
  力学的な仕事は約47%しかない
- 筋肥大の研究で主流の量の指標は「限界近くまで行ったセットの数」で、トン数ではない。
  同じ種目どうしの比較では rom は打ち消し合うので、効くのは部位別・セッション合計のように
  種目をまたぐ集計だけ。**この式は「短い種目を見つける」用途にのみ使える**と理解しておくこと
- 体格依存が大きい項目(懸垂、ディップス、腕の弧長、ステップアップの台高)は
  170cm前提を外すと±20%程度ぶれる

## 体重係数(bw)

自重種目の実効重量は `体重 × bw + 加重` で計算する(`src/domain/oneRm.js` の `effWeight`)。

すべて**可動域の中間位**の値。プッシュアップのように上端と下端で値が変わる種目があるため、
位置を固定しないと数字が揺れる。

### 原理は3つに分かれる(2026-10 に明文化)

測っている量が種目によって違う。種目を足すときは、まずどれに当たるかを決めてから値を出す。

1. **全身が並進する種目**(懸垂・チンアップ・ディップス・スクワット系・カーフ):
   **動く質量の割合**。`体重×bw+加重` の足し算が物理的に成り立つ
2. **支点まわりに全身が回る閉じた系**(腕立て系・インバーテッドロウ・アブローラー・ベンチディップス):
   **手にかかる力の実測値**(なければ静的モーメント)。レバー比はここに入るので、rom に重ねない
   (上の「レバー比の二重計上」)
3. **体の一部だけを持ち上げる開いた系**(クランチ・レッグレイズ・バックエクステンション・ノルディック):
   **体節質量 × cos(中間位)**(ノルディックだけは足首の実測)。胸に抱えたプレートや足に挟んだ
   ダンベルと同じ物差しにならないので、**ボリュームを控えめに数えるための値だと割り切る**。
   この種目群では推定1RMに意味が無い

体節質量は若年成人の生体を測った de Leva 1996 のほうが新しい(両脚 39.7%/41.8%、HAT 60.3%/58.2%。
男/女)。これに差し替えるとバックエクステンションは0.35、クランチは0.30になるが、
**2026-10 の判断で据え置いた**(差は推定の誤差の範囲で、継続利用者の数字が変わる実害のほうが大きい)。

### 実測研究が見つかったもの

| インバーテッドロウ | 0.65 | Vural et al., PLoS ONE 2023(PMC10516423)。TRXで等尺性69.5%・等張性73.4%BW。これはほぼ水平の体幹での値で、バー使用時は体幹が起きるためcos補正して0.65 |

### レバー計算による推定(実測なし)

|---|---|---|
| ベンチディップス | 0.75 | かかと支点の静的モーメント。脚(0.32BW、重心はかかと-股関節の6割)とHAT(0.68BW、重心はほぼ手の真上)の合成 → 約0.78。膝を曲げて足裏を床につける形なら約0.70 |
| バックエクステンション | 0.40 | 45度台、中間位=水平から約57度。HAT 0.68 × cos57° ≒ 0.37。ローマンチェア(水平台、中間位45度)なら0.68 × cos45° ≒ 0.48 |
| クランチ | 0.35 | 持ち上がるのは頭頸部(0.08)+両腕(0.10)+胸郭(0.22)= 約0.40。中間位のモーメント補正で0.35 |
| アブローラー | 0.45 | 膝コロ。膝支点で膝上0.88BW・重心は膝から約0.63m、手の接地は約1.3m → 0.88×(0.63/1.3) ≒ 0.43。立ちコロなら0.6-0.7 |
| ハンギングレッグレイズ | 0.30 | 両脚 0.32BW × 中間位補正、上端の骨盤の巻き上げ分を加算。**ぶら下がる体重は握力・広背筋にかかるもので腹筋の負荷ではない** |
| レッグレイズ | 0.25 | 両脚 2×0.161 = 0.32BW × cos45° ≒ 0.23 |
| ディップス | 1.00(2026-10 に0.95から変更) | 懸垂と同じ扱いに揃えた。下の注記 |
| 懸垂 / チンアップ | 1.00 | 同上 |

**懸垂・ディップスは「慣習」で1.0に揃えている(2026-10)。** 力学的には、両側の前腕と手
(de Leva で体重の約4.5%)を除いた約0.955が正しい。2026-10 までは懸垂1.0(慣習)、
ディップス0.95(物理)と根拠が混在していた。Hevy は懸垂・チンアップ・ディップス・逆立ち腕立てを
すべて体重の100%とし、加重は「体重+加重」で数える。利用者の感覚もこちらに合うので、1.0に揃えた。
同じ系統の種目(リングディップス、マッスルアップなど)を足すときも1.0にする。
過去の記録は保存時の bwFactor(0.95)を焼き込んでいるので変わらない。

**副作用(許容した)**: 履歴の推定1RMは保存時の bwFactor(0.95)で、今日のセットは1.0で計算する。
そのため更新後に初めてディップスを記録する日は、同じ加重・同じ回数でも実効重量が体重の5%
(70kgで約3.5kg)上がり、**自己ベスト更新と YOU WIN! が一度だけ出ることがある**。
過去分を再計算すると「過去の記録は当時の設定のまま残る」という約束と衝突するので、手当てしていない。

セグメント質量比(HAT 0.68、片脚 0.161、前腕+手 0.022)は広く引用される値をモデルの前提に
置いたもので、**一次出典は確認できていない**(Winter の Dempster表 / Plagenhoef et al. 1983 が
候補だが、PDFが取得できなかった)。

### 意図的に係数を付けなかった種目

| 種目 | 理由 |
|---|---|
| アシスト懸垂 | 実効負荷は「体重 − 補助」だが、`体重 × 係数 + 重量` の式では負の重量を入れないと表現できず、「補助を増やすほど記録上の重量が増える」逆転が起きる。セットの `assisted` フラグで扱う現行方針のほうが破綻が少ない |
| ケーブルクランチ / アブドミナルマシン | 体幹の自重モーメントは寄与するが、スタック重量と二重計上になる |

### `db` は「×2」の意味(2026-10 に整理)

`db: true` は「**左右それぞれ行う種目で、入力は片側の重量。集計では2倍する**」という意味に限る。
器具がダンベルであることとは別。2026-10 まではこの2つを兼ねていて、片手ラットプルダウン
(ケーブル)は `db` が無く、ボリュームと推定1RMが半分に出ていた。

- ダンベル1個を両手で持つ種目(ゴブレットスクワット、ダンベルプルオーバー、
  ダンベルオーバーヘッドエクステンション)は `db` 無しで正しい
- 片手ラットプルダウンと片手ケーブルロウは `db: true`
- `resolveIsDb` はマスターを記録の値より優先するので、**片手ラットプルダウンは過去の記録も
  ボリュームと推定1RMが遡って2倍になる**。前回との比較は全部が2倍なので崩れない
- カスタム種目は、器具がダンベルなら既定で `db` を付ける(変えていない)
- 片脚のマシン種目(スタンディングレッグカールなど)は、`db` を付けると重量の見出しが「片手」に
  なってしまうので、まだプリセットに入れていない

### 片脚種目の推定1RM(ブルガリアンスクワット、2026-10-24 に見直し、2026-10-26 に実装)

北村さんの「ブルガリアンスクワットの1RMを見直して」を受けて調べた。

**今の計算**: `実効重量 = 片手の重量 × 2`(ダンベル2個の合計)、体重は入れない。推定1RMはこれに Epley。
外部荷重だけで1RMを数えるのは研究の慣習と同じ(McCurdy らの RFESS 1RM 103 ± 21.5kg、Helme らの 5RM 84 ± 16.8kg は
どちらもバーの重量だけ)。したがって「計算が間違っている」わけではない。問題は次の2つ。

1. **回数の選び方で推定1RMが大きく変わる。** Epley は「動かしている負荷全体の何%か」と回数の関係なので、
   体重が負荷の半分以上を占める種目で外部荷重だけに当てると、軽く多く回した日ほど低く出る。
   体重70kg・動く体重を0.9とし、体重込みの真の1RMが110kgの人を Epley どおりに動かすと:

   | 同じ人の同じ日 | 今の計算(外部荷重のみ) | 体重込み(70×0.9 + 合計) |
   |---|---|---|
   | 片手10kg × 10回 | 26.7kg | 110.7kg |
   | 片手15kg × 6回 | 35.0kg(+31%) | 108.5kg |
   | 片手20kg × 2回 | 42.7kg(+60%) | 109.9kg |

   このアプリの自己ベスト・⚡・YOU WIN!・比較の行の緑はすべて推定1RMで決まるので、
   **重い日に回数を落とすだけで自己ベストが出て、高回数の日は実力が同じでも負けに見える。**
   バーベルスクワットでも同じ歪みはあるが、外部荷重が体重より大きいので小さい
2. **ダンベルを持たない(重量0)日は、推定1RMもボリュームも0になる。** 家で自重だけでやる人の記録が何も残らない

**片脚で何kgを支えているか(文献)**

- Helme, Emmonds & Low, JSCR 2022(26名・715レップ、フォースプレート2枚): 前足が鉛直力全体の **84.36 ± 3.6%**。
  後ろ足の力は後ろ脚の質量とほぼ無相関で、後ろ足は運動の負荷に寄与していないと結論
  (accepted manuscript を一次確認。Leeds Beckett eprint 6750)
- Helme, Emmonds, Bishop & Low, JSCR 2019: RFESS 5RM の妥当性・信頼性。前足の負担 84.41 ± 5.40%(eprint 6081 を一次確認)
- DeForest ら(Helme 2019 経由の二次情報): 同じ外部荷重(バックスクワット1RMの42.5%)で、RFESS のピーク鉛直力は
  バックスクワット(両脚の合計)とほぼ同じ(1412 vs 1415N)
- 前足の84%は**体重と外部荷重の両方にかかる**(鉛直力の総和 = 体重 + 荷重)。つまり前脚にとって、体重1kgとダンベル1kgは同じ重さ。
  体重を外して数える理由は力学的には無い
- 片脚種目の1RM比(RFESS ÷ バックスクワット)を同じ被験者で測った研究は見つからなかった。
  別集団どうしの比較で約0.66(McCurdy 1.17kg/kg ÷ Baker & Newton 1.78kg/kg)。Helme 2019 は「片脚で両脚の50%超」と書いている

**体重係数の値: 0.9**(原理1「全身が並進する種目」の、動く質量の割合)

- 前脚の下腿と足(de Leva 1996 の男性値で約5.7%)はほぼ動かないので除く → 約0.94
- 後ろ脚の下腿と足はベンチに乗っていて、股関節の下降の一部しか動かない → さらに数%引く
- 0.05刻みの精度は無いので **0.9** とする。84%(前脚の負担割合)は体重と荷重に同じく掛かる共通の倍率なので、
  `体重 × 係数 + 荷重` の比には入れない(入れると荷重のほうにも0.84を掛けないと釣り合わない)
- ランジ・ステップアップも同じ考え方で、同じ系列として揃える(ステップアップは後ろ脚も持ち上げるので理屈の上では少し大きいが、推定の誤差の範囲)

**決定(2026-10-26、北村さんの「はい」)と実装**

- ブルガリアンスクワット・ランジ・ステップアップに `bw: 0.9`。`db: true` と併用する(片手の重量を入力し、2個分を数える)
- `effWeight` を「体重を足してから2倍」から **「ダンベルだけ2倍して体重を足す」** に直した(`体重 × 係数 + 片手 × 2`)。
  これで記録画面の⚙で `db` 種目に「自重種目」を付けたときに体重まで2倍になる穴(下の「`db` は ×2 の意味」の末尾)も塞がった。
  ⚙でそうしていた記録(bwFactor 0.7 など)は、読み直すと体重の分が半分になる。実態に合う向きの変化なので許容した
- **過去の記録は `backfillBwFactor`(`src/domain/coefficients.js`)で揃える。** この3種目で保存値が0(または無い)の記録にだけ、
  今の係数(上書き込み)を入れる。通すのは読み込み(`migrateWorkouts`)・バックアップの復元と取り消し・下書きの復元。
  次に保存したときに記録にも書かれる(計算するときだけ当てる形にすると、`ex.bwFactor` を読む十数か所を全部直す必要があり、
  一つ漏れると画面ごとに数字が食い違うため)。重量・回数は変わらない。上書きで体重係数を0にしている人の記録には入れない。
  「記録側の値は当時のまま」の原則の、名前を限った例外。
  **通すのは、この版をその端末で初めて開いた時刻(`leg-bw-since-v1`)より前の記録だけ**(`beforeLegBw`)。
  保存値0には「変更前の記録」と「変更後に⚙で自重を外した日の記録」の2つの意味があり、毎回の読み込みで後者まで書き換えると、
  ⚙で付け直したり「元に戻す」を押したりした日に、外していた日の1RMが体重の分だけ跳ねて記録に焼き付く(reviewer 指摘)。
  別の端末でバックアップを復元すると、その端末で初めて開いた時刻が線になるので、それより前の記録はすべて揃える側に入る
- 重量欄の見出しは「加重 kg/片手」(記録画面と Watch)。AIコーチの相談文は「(片手の加重。体重は含まない)」。
  共有の文は、自重の分を先に見て「体重込」の実効重量(左右計)で書く。比較カード・履歴の1RMの単位はもともと「体重込」を優先していた
- 記録画面の⚙で「自重種目」を付け直したときと、設定タブで器具を「ダンベル」に戻したときは、内蔵の既定(片脚なら0.9)に戻す
  (以前は0.7固定・0固定で、片脚の種目で外して付け直すと0.7の上書きが残った)
- 投稿用の画像の「BW+10」は片手の値のまま。画像ではダンベルの種目はもともと片手で書いているので、それに揃えた
- 片脚以外に `db` と `bw` の両方を持たせるときは、`BW_BACKFILL_NAMES` に名前を足すこと(テストで一致を縛ってある)
- 版番号は上げていない(1.4.4 の審査待ちのため)。次の版に入る

**残した課題**

- ⚙の説明文「重量は体重×係数＋加重」は片手入力の種目では「＋加重×2」になる。2つ目の説明文で補っている
- 変更前に設定タブで器具を変えたことがある人は、上書きに `bw: 0` が残っていて、0.9 が届かない(数字は不連続にならない)。⚙で付ければ0.9になる
- 片脚の1RMをバックスクワットの1RMと並べると、体重込みの分だけ大きく見える(例: 体重70kgで110kg)。種目どうしを比べる画面は無いので手当てしていない

### 2026-10 に種目マスターを動かしたときの、継続利用者への影響

- **ステップアップの部位(臀部→大腿四頭筋)は、続けて記録している利用者には効かない。**
  「今日のメニュー」の `buildMenuItem` が `muscle: prevEx.muscle ?? cfg.muscle` と記録の部位を
  引き継ぐため。新しく始める利用者と、手で種目を足したときだけ大腿四頭筋になる。許容した
  (部位は rom / bw と違って利用者が⚙で決める値でもあり、記録側を優先する既存の設計を崩さない)
- **内蔵に足した19種目と同じ名前のカスタム種目は、読み込み時に上書き(exerciseOverrides)へ移す**
  (`absorbBuiltinNameClash`、src/domain/coefficients.js)。放っておくと一覧に2行出るうえ、
  計算は内蔵側・設定画面の編集はカスタム側を見るので、直しても効かなくなる。利用者が決めていた
  値のうち内蔵の既定と違うものだけを残すので、例えば db 無しで作っていた「片手ケーブルロウ」は
  `db: false` の上書きになり、過去のボリュームは変わらない
- 内転筋を足したことで、新しい利用者がプリセットの脚の Day で「おまかせで入れる」を押すと、
  5枠が各部位の1種目目で埋まり、以前2周目で入っていたレッグプレスの代わりにヒップアダクションが入る

`db: true` と `bw` の併用は `tests/exerciseCoefficients.test.js` が禁止している。
**ただし縛れているのは種目マスターの値だけ**で、ランタイムでは同じ状態を作れる:
記録画面の⚙の「自重種目」チェックは種目の `db` を見ておらず、ダンベルシュラッグ
(`db: true`)でONにすると `bwFactor 0.7` × `isDb true` になる。2026-10-26 までは実効重量が
`(体重×0.7 + 加重) × 2` になっていたが、`effWeight` を直して `体重×0.7 + 加重×2` になった
(上の「片脚種目の推定1RM」)。マスターで `db` と `bw` を両方持つのは片脚の3種目だけ。

## 値の優先順位

```
ユーザーの調整 > カスタム種目の定義 > 種目マスターの既定値
```

解決は `src/domain/coefficients.js` の `resolveCoefficients(name, lookup)`。
`lookup` には **`findExercise` を渡す**(`allExercises` = 内蔵 + カスタム に
`exerciseOverrides` をマージ済みの索引)。

**記録側に焼き込まれた値は優先順位に入らない。** ここはv102で変えた。`saveWorkout` は
毎回 `rom`/`bwFactor` を記録に書き込むが、それは「その日の計算に使った値」のスナップショット
であって、ユーザーがそう決めたという意思表示ではない。以前はここから読み戻していたため、
**一度でも記録した種目はマスターの既定値を更新しても永久に古い値のまま回り続けていた**
(しかも `saveWorkout` がまた書き戻すので自己増殖する)。

### 直すときに踏んだ落とし穴(3つとも実際にやった)

1. **`lastConfig` だけ直しても効かない。** 「今日のメニュー」は `buildMenuItem` が
   `prevEx.rom ?? cfg.rom` と記録を直読みしており、`saveWorkout` が必ず数値を書くため
   `??` は絶対にフォールバックしない。しかもv101で「今日のメニュー」は前回の実記録を
   最優先にしたので、**継続ユーザーが毎日通るのはこちら**。両方直さないと、
   手で種目を足したときとメニューから始めたときで同じ種目に別の係数が付く
2. **`dbLookup` はカスタム種目を見ない**(`DB_BY_NAME` + `EXERCISE_OVERRIDES` のみ)。
   ここを索引に使うと自重のカスタム種目が `bwFactor: 0` になり、実効重量もボリュームも
   推定1RMも0のまま記録される。`findExercise` を使うこと
3. **⚙が無編集でも上書きを書くと、潰したはずのバグをUI経由で再生産する。**
   フィールドを触って他所をタップしただけで `exerciseOverrides` が作られ、以後その種目に
   マスターの更新が永久に届かなくなる。**値が変わったときだけ書く**

記録画面の⚙での調整は、そのままだと翌日に残らないので `updateCustomExercise` で
`exerciseOverrides`(カスタム種目なら `customExercises` の実体)にも書いている。
「自重種目」チェックボックスも ON/OFF の両方を書く。書かないと OFF が翌日に残らず、
マスターに `bw` を持つ種目では 0.7 が復活して重量欄の意味が「加重」に戻る。

### 既知の穴(未修正)

- **`resolveRom` のフォールバックだけは `dbLookup` のまま**で、カスタム種目を見ない。
  `rom` フィールドを持たない古いバックアップを復元したカスタム種目は、集計時にカスタム側の
  `rom` が無視されて1.0で数えられる。`resolveRom` はコンポーネント外の定数で
  `customExercises` に触れないため、直すなら `volumeDeps` 経由の注入が要る
- **種目マスターから消した種目は係数を失う。** 記録側から読み戻さなくなったので、
  自作の自重種目を設定タブで削除すると、翌日「今日のメニュー」にはその種目が並ぶのに
  (`buildMenuItem` は `workouts` から拾うので削除の影響を受けない)`bwFactor: 0` になり、
  ボリュームも推定1RMも実質0のまま記録される。警告は出ない
- **記録画面の⚙は「今日の記録の設定」から「種目のグローバル設定」に意味が変わった**が、
  UIの見た目は変わっていない。今日だけ試すつもりの調整が将来の既定値になる
- **カスタム自重種目で `bw: 0` になると復帰が難しい。** 内蔵種目は「元に戻す」ボタンが出るが、
  カスタム種目は実体を書き換えるためボタンが出ず、`e.bw > 0` の条件で入力欄自体も消える
  (記録画面の⚙のチェックボックスなら0.7で復帰できる)

## 過去の記録への影響

**基本的に壊れない。** `src/domain/volume.js` は記録側の `rom`/`bwFactor` を読み、
`saveWorkout` がそれを保存時に焼き込んでいるため、過去の集計は変わらない。

**ただし `rom` には例外がある。** `resolveRom` は保存値が無い(`undefined`)場合に
現在のマスター値へフォールバックする:

```js
const resolveRom = (name, storedRom) => {
  const v = parseFloat(storedRom);
  if (!isNaN(v) && v > 0) return v;
  return dbLookup(name)?.rom ?? 1.0;   // ← ここ
};
```

そのため **`rom` フィールドを持たない古い記録は、過去のボリュームが遡って変わる**
(週間の部位別集計・`compareBase`・`sameSplitSessions`・履歴一覧はすべて保存値ではなく
再計算するため)。該当するのは `rom` が無かった時代のバックアップJSONを復元した場合など。
`bwFactor` は `setVolume` 側でフォールバックしないので遡らない。**romだけが非対称**。

### 上部バーのゲージへの副作用

**上部バーのボリュームゲージは「今日 vs 同じ分割日の直近3回平均」で比較する**ため、
係数を下げた種目をやっていた人は、実力が変わっていないのに数週間「基準に届いていない」と
表示される。データは壊れないので許容とした(過去分を再計算すると「過去の記録は当時の
設定のまま残る」という既存の約束と衝突する)。

### 見た目の変化

`ROM×0.65` のようなバッジが記録行に出るのは `resolveRom(...) < 1` のときなので、
**新たに7種目(プッシュアップ / インバーテッドロウ / ラックプル / ヒップスラスト /
クランチ / ケーブルクランチ / アブドミナルマシン)でバッジが表示される。**
ユーザーから見て最初に目に入る変化はここ。

2026-10 にプッシュアップとインバーテッドロウから rom を外したので、この2種目のバッジは
新しい記録では出ない(保存済みの記録には rom が残っているので、過去の行には出る)。
同時に追加したヒップスラストマシン / スミスマシンヒップスラスト / スミスマシンカーフレイズでは出る。

### bwとromを両方下げた種目の複合効果

表を別々に見ると読み取れないので、掛け合わせた結果を書いておく(体重70kg)。

| 種目 | bw | rom | 集計ボリュームの変化 |
|---|---|---|---|
| クランチ | 0.4 → 0.35 | 1.0 → 0.5 | 約 **-56%**(560 → 245kg / 20回) |
| プッシュアップ | 0.65 → 0.70 | 1.0 → 0.65 | 約 **-30%**(910 → 637kg / 20回) |
| インバーテッドロウ | 0.7 → 0.65 | 1.0 → 0.75 | 約 **-30%**(735 → 512kg / 15回) |

プッシュアップは **bwを上げたのにボリュームは減る**。表だけ見ると読み取れないので注意。
(プッシュアップとインバーテッドロウの rom は、2026-10 に二重計上と分かって外した。今は bw だけが効く)
