# 多言語化(日本語 / 英語)の方針

対象: `index.html` の UI 全体、種目マスター、周辺ページ、App Store 掲載情報。
2026-08-17 の検討で方針を決定。実装はまだ着手していない。

## 目的

**英語圏への App Store 配信**。アプリ内 UI の英語化だけでなく、
`privacy.html` / `support.html` / App Store 掲載情報・スクリーンショットの英語版まで含む。

## 現状(実測)

`#appsrc` 内の翻訳対象リテラルは延べ 663 本 / ユニーク 378 本 / 計 5,751 文字。
i18n 基盤は存在せず、文字列は JSX に直書き。`<html lang="ja">` は固定値。

ユニーク 378 本のうち **約 120 本は画面文言ではなく「ドメイン語彙」**である。

| 種別 | 数 | 定義場所 |
|---|---|---|
| 種目名 | 95 | `EXERCISE_DB`(index.html) |
| 部位名 | 14 | `MUSCLES`(index.html) |
| 器具名 | 6 | `EXERCISE_DB` の `eq` |
| 分割プリセット名・曜日など | 約 5 | `SPLIT_PRESETS` ほか |

`#appsrc` の外にも対象がある: `manifest.json` / `privacy.html` / `support.html` /

`i18n.js` に依存できない。別扱いが要る)。

## 決定 1: 種目名・部位名は「表示だけ」英語化する

**保存フォーマットは日本語名のまま据え置き、表示のときだけ辞書を引く。**

### なぜか

日本語の種目名・部位名は表示文字列ではなく**データのキーとして永続化されている**。

- 記録は `{ name: "バーベルベンチプレス" }` として保存される。SQLite では
  `workout_exercises.name` という **インデックス付きの TEXT カラム**(`src/domain/db/schema.js`)
- `exerciseNotes` / `exerciseOverrides` / `recentNames` / `customExercises` がすべて名前キー
- `split.days[].muscles` に `"胸"` などの部位名が文字列で入る
- `DB_BY_NAME` / `ALIASES`(index.html:346-351)も名前ベース
- バックアップ JSON にもそのまま出る

`EXERCISE_DB` を英語に差し替えると、既存ユーザーの履歴が全部「未知の種目」になり、
前回比較・PR・ボリューム集計が**エラーも出さずに切れる**。バックアップの相互互換も壊れる。

日本語名を事実上の ID として扱い、`表示名テーブル[日本語名][lang]` を 1 枚足すだけにすれば、
`src/domain/storage.js` / SQLite 層 / `backupValidation.js` / 既存テストに一切触らずに済む。
将来ちゃんとした ID に切り直すなら、その時に移行を書く(git 履歴とこのメモが根拠になる)。

### 副作用として対応が要るもの

- 種目検索のフィルタ(index.html:2409 付近)は `e.n.includes(q)` で日本語名だけを見ている。
  表示名でも引けるよう OR 条件を足す(英語 UI でも日本語名で引ける状態を維持する)
- カスタム種目はユーザー入力なので翻訳しない。そのまま表示する
- テキスト共有の出力(index.html:1754 付近)は表示言語に従わせる

## 決定 2: kg / lb を同時に対応する。ただし言語とは別スイッチ

英語圏配信では米国の lb が事実上必須。ただし
「日本語 UI だが lb」「英語 UI だが kg」はどちらもあり得るので、
**言語設定(`profile.lang`)と単位設定(`profile.unit`)は独立させる**。

### 保存は常に kg。入力・表示のみ換算する

種目名と同じ発想で、保存フォーマットを触らない。

- `LB_PER_KG = 0.45359237`
- lb 表示は **0.5 lb 刻みで丸める**
- `profile.bodyweight` も kg 保存・表示換算。`effWeight()` は kg で計算されるので**無変更**
- ボリューム・推定 1RM・PR もすべて kg で計算し、**表示の瞬間だけ**換算。
  よって `src/domain/oneRm.js` と `src/domain/volume.js` は無変更

**なぜ保存を kg に固定するか**: 「前回と同じ重量ならセット行に RIR の差分を出す」という
同一負荷判定が浮動小数の比較に依存している。単位混在で保存すると、この比較が
往復誤差で無言で壊れる。比較は必ず保存値(kg)で行う。
lb 入力は 2.5 lb や 5 lb 刻みなので kg 換算値は決定的になり、同じ入力は必ず同じ kg 値になる。
表示側の 0.5 lb 丸めが往復誤差を吸収する。

### 刻み幅は単位ごとにテーブルを分ける

`recommendedIncrement()`(index.html:372-379)の分岐はすべて kg 前提
(マシン 5kg / 単関節ダンベル片手 1kg / 単関節その他 2.5kg / 多関節ダンベル片手 2kg / その他 2.5kg)。
lb 用に別テーブルを持つ。lb の実機は 5 lb 刻みのプレートとマシンが基本:

| | kg | lb |
|---|---|---|
| マシン | 5 | 10 |
| 単関節・ダンベル(片手) | 1 | 2.5 |
| 単関節・その他 | 2.5 | 5 |
| 多関節・ダンベル(片手) | 2 | 5 |
| 多関節・その他 | 2.5 | 5 |

`profile.defIncrement` は kg で保存し、設定画面では表示単位で見せる。

## 決定 3: i18n ライブラリは入れない

i18next 等はビルド前提で、zero-build の設計原則(CLAUDE.md)と
「外部ホストへのリクエストを足さない」という制約の両方に反する。

`src/domain/i18n.js` を新規追加する。素のグローバルスクリプト(import も module.exports も使わない)。

```js
const I18N = { ja: { ... }, en: { ... } };      // UI 文言
const EX_NAMES    = { "バーベルベンチプレス": "Barbell Bench Press", ... };
const MUSCLE_NAMES = { "胸": "Chest", ... };
const EQ_NAMES     = { "バーベル": "Barbell", ... };
let LANG = "ja";
const t = (key, params) => ...;                  // 未定義キーは key をそのまま返す(白画面より安全)
const exName = (jaName) => LANG === "ja" ? jaName : (EX_NAMES[jaName] || jaName);
```

- **追加したら参照元 3 箇所を揃える**: `index.html` の `LIBS` / `sw.js` の `APP_ASSETS` /
  `scripts/sync-www.js` の `DOMAIN_FILES`。`cache.addAll()` は 1 つでも失敗すると
  全体が reject し、SW が永久に activate しない(CLAUDE.md 参照)
- 言語の決定順: `profile.lang` > `navigator.language` > `ja`
- `<html lang>` は起動時に書き換える
- **ブートブロックの文言だけは例外**。`i18n.js` の読み込みより前に走るので、
  `navigator.language` を直接見て ja/en を出し分ける小さな分岐を置く
- `profile` は SQLite の `settings` テーブルに JSON 1 行で入っているので、
  `lang` / `unit` を足してもスキーマ移行は不要

### どこで換算するか

`today`(記録中)と編集中の記録は、**保存前の文字列を表示単位のまま**持っている。
入力欄の値を毎回 kg に直して描き戻すと、入力途中に値が化けて使い物にならないため。
よって換算は次の 2 種類の境界だけで行う。

| 向き | 場所 |
|---|---|
| kg → 表示単位(`wStr`) | 前回記録からセットを組み立てる 5 箇所(`startAutoMenu` / `initialSetsFor` / `addExercise` / `beginEditWorkout`) |
| 表示単位 → kg(`fromU`) | 保存する 2 箇所(`saveWorkout` / `saveEditWorkout`)と、`today` から計算する 5 箇所(`liveVolume` / `liveBest1RM` / `liveMaxWeight` / セット行の推定 1RM) |

読み取り専用の表示(ボリューム・推定 1RM・PR・グラフ・共有テキスト・CSV)は
保存値が kg なので `toU` / `wU` を通すだけ。グラフはデータ生成の時点で表示単位に直しており、
軸とツールチップは何も知らなくてよい。`oneRm.js` / `volume.js` / `storage.js` / `db/` は無変更。

### 丸めをどこに置くか(実際に2回間違えた)

- **`wU` を kg でも 0.5 丸めしていた。** 62.3kg のように 0.5 刻みでない重量を入れている
  既存ユーザーの記録を、表示するだけで 62.5 に書き換えてしまう。**換算が入るときだけ丸める**に変更。
- **`fromU` で kg を小数 1 桁に丸めた。** 入力欄の桁数対策のつもりが集計に誤差が乗り、
  135lb × 8 が 1,080lb ではなく **1,079lb** と出た。`fromU` では丸めず、
  単位を切り替える経路(`convWeightStr`)だけで丸めるように変更。

### 刻み幅に lb 専用テーブルは要らなかった

kg の既定値を 2.5lb 刻みに丸めると、そのまま英語圏の実機の刻みになる
(マシン 5kg→10lb / 単関節ダンベル片手 1kg→2.5lb / 単関節 2.5kg→5lb / 多関節ダンベル 2kg→5lb)。
`incU()` の 1 行で済み、ユーザーが調整した刻みも比例して反映される。

なお `adjustSet()` とセット行の `inc` は**どこからも呼ばれていない**(± の UI が存在しない)。
`round()` も同様。Phase 1.5 では消していないが、削除して問題ない。

### 単位を切り替えたときの記録中の値

`today` は表示単位の文字列なので、切り替えの瞬間に `convWeightStr` で読み替える。
これを入れないと「135」が lb から kg に化けて別物の記録になる。

**読み込み完了(`loaded` が false→true)の 1 回目では換算してはいけない。**
起動直後は端末の言語から決めた既定単位で描画され、その後に保存済みの `profile.unit` が入る。
この変化を「ユーザーが切り替えた」と誤認すると下書きを二重に換算する
(実際にそれで 135lb が 297.5lb に化けた)。`loaded` が false の間は前回値の記録もしないことで防いでいる。

## Phase 2 の実装記録(v85)

UI 文言 333 キーを `src/domain/i18n.js` に集約し、`#appsrc` の全画面を `t()` 経由にした。
英語表示時に画面へ残る日本語はゼロ(実機で全タブを確認済み)。

### 文言テーブルの持ち方を変えた

言語別に 2 つのオブジェクトを並べる形(`I18N.ja` / `I18N.en`)から、
**キーごとに ja / en を隣り合わせで書く `STRINGS`** に変更した。
300 本超を目視で対応付けるのは無理で、片方だけ直す・片方に足し忘れるのが必ず起きる。

```js
const STRINGS = { "common.save": { ja: "保存", en: "Save" }, ... };
const I18N = { ja: {}, en: {} };   // STRINGS から組み立てる
```

`t()` が引くのは従来どおり `I18N` なので、呼び出し側は無変更。
テストは 2 つ追加した:

- `STRINGS` の全エントリが ja / en を両方持つこと
- **プレースホルダの集合が ja / en で一致すること**。`{name}` を `{n}` に書き間違えると
  差し込みが効かず画面に `{name}` がそのまま出る。訳を直すときに一番起きやすい壊れ方なので機械的に落とす

### 置換のやり方

`index.html` への適用は、**置換前の文字列と出現回数を宣言して当てる**スクリプトで行った。
1 つでも想定と違えば何も書かずに落ちるので、静かに空振りしない。
実際にこれで「`aria-label="上へ移動"` は 3 箇所ある」「`回数` のラベルは記録画面と履歴編集の 2 箇所」を
取りこぼさずに済んでいる。

### 翻訳で構造を変えた箇所

- **`<strong>` を諦めた 1 箇所。** 「{重量} で **{n}回連続**」は英語だと
  "**{n} sessions** in a row at {重量}" と語順が変わり、太字の範囲を保てない。
  1 文にまとめ、強調は span 側の `fontWeight` に移した
- **Recharts の `<Legend>` は `dataKey` をそのまま描く。** データキー(`最大重量` / `推定1RM`)は
  内部識別子として日本語のまま残し、`<Legend formatter>` と `<Tooltip formatter>` で表示名だけ差し替えた
- **`・` は英語に混ぜない。** 部位と器具の区切りを `common.sep` にして、英語では ` · ` を使う
- **保存される名前は翻訳しない。** アプリが自動で付ける分割名(`マイメニュー` / `カスタム分割`)と、
  部位未設定の集計キー(`未設定`)は `split.name` / グループキーとして保存・集計に使われるので、
  日本語のまま保存し `SPLIT_NAMES_EN` / `MUSCLE_NAMES_EN` 経由で表示だけ英語にした

### useMemo に `lang` を足す必要があった

翻訳済みの文字列を組み立てている `useMemo`(`compareBase` / `autoMenu` / `weeklyVolumeTrend` /
`backupNag`)は、依存配列に `lang` が無いと**言語を切り替えても古い言語のまま残る**。
値ではなく文字列を memo する場所は依存に言語が要る。

## Phase 3 の実装記録(v86)

### 見つけた P0: iOS 版が Phase 1 以降ずっと起動しない状態だった

`scripts/sync-www.js` には**ファイルを並べる場所が 2 つ**あった。
コピー対象の `DOMAIN_FILES` と、生成する `index.html` に書き出す `<script src>` の並び(手書き)。
Phase 1 / 1.5 で `i18n.js` と `units.js` を前者にだけ足していたため、
**www/ にファイルは置かれるが読み込まれない**状態になっていた。
`t()` も `exName()` も `wU()` も未定義なので、iOS 版は最初のレンダリングで落ちる。

見逃した理由が 2 つある:

- Web 版(リポジトリ直下配信)は `index.html` の `LIBS` 経由で読むので**まったく無症状**
- `tests/sync-www.test.js` は「`<script src>` が指すファイルが実在するか」しか見ておらず、
  **逆方向(コピーしたのに読み込まれていない)を見ていなかった**

対処:

- `<script src>` の並びを `VENDOR_FILES` / `DOMAIN_FILES` / `DB_DOMAIN_FILES` から生成するようにし、
  手で並びを書く場所そのものを無くした
- 逆方向のテストを追加(www/ にある `.js` が全部 `<script src>` に出てくること)。
  実際に修正前の状態を再現して、このテストが落ちることを確認済み
- 読み込み順が `index.html` の `LIBS` と一致することも縛った(ドメインファイル間の依存が崩れないように)
- CLAUDE.md の「参照元 3 箇所」の記述を、この 4 箇所目があった経緯ごと更新した

### manifest は言語ごとにファイルを分けた

manifest は 1 ページに 1 つしか指定できず、GitHub Pages にコンテントネゴシエーションは無い。
`manifest.json` / `manifest.en.json` の 2 つを置き、`<head>` 内のスクリプトで
`navigator.language` を見て `href` を書き換える。`<head>` で走らせるのは、
ブラウザが manifest を読みに行く前に確定させるため。`<meta name="description">` も同時に差し替える。

iOS(Capacitor)は manifest を使わないので、これは Web PWA のインストール表示だけの話。

### privacy.html / support.html は 1 つの URL で日英を出し分ける

App Store Connect はロケールごとに URL を登録できるが、
**1 つの URL が両言語を出せる方が登録も保守も単純**なので、ページ側で切り替える方式にした。
`<section data-lang="ja">` / `<section data-lang="en">` を端末の言語で出し分け、
右上のボタンで手動切り替え(選択は localStorage に保持)。
JS が無効なら両言語とも表示される — 法的文書は隠れるより出る方が安全。

### iOS 側

`Info.plist` に `CFBundleLocalizations`(en / ja)を足した。
UI の切り替えは WebView 側(`i18n.js`)でやるので `.lproj` は持たないが、
これを書かないと**App Store の製品ページに「言語: 英語」しか出ず、日本語対応が伝わらない**。
アプリ名 `KURABELL` は言語によらないので `InfoPlist.strings` は不要。

### 残: スクリーンショット

App Store のスクリーンショットは**ローカライズごとに必要**で、英語用を登録しないと
日本語のものが英語圏に表示される。Xcode シミュレータで英語表示にして撮り直す必要があり、

### ついでに直した既存の不具合: 部分一致で候補が出なかった

種目選択の絞り込みリストが `{!(search.trim() && !findExercise(search.trim())) && (...)}` で
出し分けられており、**検索語が種目名と完全一致(またはエイリアス一致)でない限りリストが出ず、
「カスタム種目として追加」パネルに丸ごと切り替わっていた**。日本語で「ベンチ」と打っても
候補が 0 件だったので Phase 1 で入った問題ではないが、この経路では `exMatches()` が
一度も呼ばれず、英語で "bench" と打っても候補が出ないため、多言語化の意味が無くなる。

**候補リストは常に出し、カスタム追加パネルはその下に並べる**ように変えた。排他にしなかったのは、
既存種目と部分一致する名前(「カール」など)で新しくカスタム種目を作りたい場合を潰さないため。
同じ出し分けが「種目と種目の間に挿入」パネルにもあったので、そちらも同様に直している。
種目差し替えと種目設定の検索には元からこのゲートが無く、変更していない。
