# 多言語化(日本語 / 英語)の方針

対象: `index.html` の UI 全体、種目マスター、周辺ページ、App Store 掲載情報。
2026-08-17 の検討で方針を決定。実装はまだ着手していない。

## 目的

**英語圏への App Store 配信**。アプリ内 UI の英語化だけでなく、
`privacy.html` / `support.html` / App Store 掲載情報・スクリーンショットの英語版まで含む。

## 現状(実測)

`#appsrc` 内の翻訳対象リテラルは延べ 663 本 / ユニーク 378 本 / 計 5,751 文字。
i18n 基盤は存在せず、文字列は JSX に直書き。`<html lang="ja">` は固定値。

ユニーク 378 本のうち **約 120 本は画面文言ではなく「ドメイン語彙」**である。

| 種別 | 数 | 定義場所 |
|---|---|---|
| 種目名 | 95 | `EXERCISE_DB`(index.html) |
| 部位名 | 14 | `MUSCLES`(index.html) |
| 器具名 | 6 | `EXERCISE_DB` の `eq` |
| 分割プリセット名・曜日など | 約 5 | `SPLIT_PRESETS` ほか |
| **純粋な UI 文言** | **約 260** | JSX 全域 |

`#appsrc` の外にも対象がある: `manifest.json` / `privacy.html` / `support.html` /
`APPSTORE.md` / **ブートブロックの起動エラー文言**(index.html 冒頭。Babel より先に走るので
`i18n.js` に依存できない。別扱いが要る)。

## 決定 1: 種目名・部位名は「表示だけ」英語化する

**保存フォーマットは日本語名のまま据え置き、表示のときだけ辞書を引く。**

### なぜか

日本語の種目名・部位名は表示文字列ではなく**データのキーとして永続化されている**。

- 記録は `{ name: "バーベルベンチプレス" }` として保存される。SQLite では
  `workout_exercises.name` という **インデックス付きの TEXT カラム**(`src/domain/db/schema.js`)
- `exerciseNotes` / `exerciseOverrides` / `recentNames` / `customExercises` がすべて名前キー
- `split.days[].muscles` に `"胸"` などの部位名が文字列で入る
- `DB_BY_NAME` / `ALIASES`(index.html:346-351)も名前ベース
- バックアップ JSON にもそのまま出る

`EXERCISE_DB` を英語に差し替えると、既存ユーザーの履歴が全部「未知の種目」になり、
前回比較・PR・ボリューム集計が**エラーも出さずに切れる**。バックアップの相互互換も壊れる。

日本語名を事実上の ID として扱い、`表示名テーブル[日本語名][lang]` を 1 枚足すだけにすれば、
`src/domain/storage.js` / SQLite 層 / `backupValidation.js` / 既存テストに一切触らずに済む。
将来ちゃんとした ID に切り直すなら、その時に移行を書く(git 履歴とこのメモが根拠になる)。

### 副作用として対応が要るもの

- 種目検索のフィルタ(index.html:2409 付近)は `e.n.includes(q)` で日本語名だけを見ている。
  表示名でも引けるよう OR 条件を足す(英語 UI でも日本語名で引ける状態を維持する)
- カスタム種目はユーザー入力なので翻訳しない。そのまま表示する
- テキスト共有の出力(index.html:1754 付近)は表示言語に従わせる

## 決定 2: kg / lb を同時に対応する。ただし言語とは別スイッチ

英語圏配信では米国の lb が事実上必須。ただし
「日本語 UI だが lb」「英語 UI だが kg」はどちらもあり得るので、
**言語設定(`profile.lang`)と単位設定(`profile.unit`)は独立させる**。

### 保存は常に kg。入力・表示のみ換算する

種目名と同じ発想で、保存フォーマットを触らない。

- `LB_PER_KG = 0.45359237`
- lb 表示は **0.5 lb 刻みで丸める**
- `profile.bodyweight` も kg 保存・表示換算。`effWeight()` は kg で計算されるので**無変更**
- ボリューム・推定 1RM・PR もすべて kg で計算し、**表示の瞬間だけ**換算。
  よって `src/domain/oneRm.js` と `src/domain/volume.js` は無変更

**なぜ保存を kg に固定するか**: 「前回と同じ重量ならセット行に RIR の差分を出す」という
同一負荷判定が浮動小数の比較に依存している。単位混在で保存すると、この比較が
往復誤差で無言で壊れる。比較は必ず保存値(kg)で行う。
lb 入力は 2.5 lb や 5 lb 刻みなので kg 換算値は決定的になり、同じ入力は必ず同じ kg 値になる。
表示側の 0.5 lb 丸めが往復誤差を吸収する。

### 刻み幅は単位ごとにテーブルを分ける

`recommendedIncrement()`(index.html:372-379)の分岐はすべて kg 前提
(マシン 5kg / 単関節ダンベル片手 1kg / 単関節その他 2.5kg / 多関節ダンベル片手 2kg / その他 2.5kg)。
lb 用に別テーブルを持つ。lb の実機は 5 lb 刻みのプレートとマシンが基本:

| | kg | lb |
|---|---|---|
| マシン | 5 | 10 |
| 単関節・ダンベル(片手) | 1 | 2.5 |
| 単関節・その他 | 2.5 | 5 |
| 多関節・ダンベル(片手) | 2 | 5 |
| 多関節・その他 | 2.5 | 5 |

`profile.defIncrement` は kg で保存し、設定画面では表示単位で見せる。

## 決定 3: i18n ライブラリは入れない

i18next 等はビルド前提で、zero-build の設計原則(CLAUDE.md)と
「外部ホストへのリクエストを足さない」という制約の両方に反する。

`src/domain/i18n.js` を新規追加する。素のグローバルスクリプト(import も module.exports も使わない)。

```js
const I18N = { ja: { ... }, en: { ... } };      // UI 文言
const EX_NAMES    = { "バーベルベンチプレス": "Barbell Bench Press", ... };
const MUSCLE_NAMES = { "胸": "Chest", ... };
const EQ_NAMES     = { "バーベル": "Barbell", ... };
let LANG = "ja";
const t = (key, params) => ...;                  // 未定義キーは key をそのまま返す(白画面より安全)
const exName = (jaName) => LANG === "ja" ? jaName : (EX_NAMES[jaName] || jaName);
```

- **追加したら参照元 3 箇所を揃える**: `index.html` の `LIBS` / `sw.js` の `APP_ASSETS` /
  `scripts/sync-www.js` の `DOMAIN_FILES`。`cache.addAll()` は 1 つでも失敗すると
  全体が reject し、SW が永久に activate しない(CLAUDE.md 参照)
- 言語の決定順: `profile.lang` > `navigator.language` > `ja`
- `<html lang>` は起動時に書き換える
- **ブートブロックの文言だけは例外**。`i18n.js` の読み込みより前に走るので、
  `navigator.language` を直接見て ja/en を出し分ける小さな分岐を置く
- `profile` は SQLite の `settings` テーブルに JSON 1 行で入っているので、
  `lang` / `unit` を足してもスキーマ移行は不要

- `openYouTube` の引数名が `exName` で、グローバル関数 `exName()` を隠していたので `name` に改名した

### 既知の制約: 起動画面は端末の言語に従う

起動画面(スピナー・エラー)の文言は `i18n.js` より前に走るので、`navigator.language` を
直接見る小さな辞書(`BT`)を index.html 内に持っている。保存済みの `profile.lang` はこの時点では
読めない(iOS では Preferences / SQLite が非同期)。**日本語端末で英語を選んでいる人には、
起動の一瞬だけ日本語の起動画面が出る。**アプリ本体が立ち上がれば英語になる。

### ついでに直した既存の不具合: 部分一致で候補が出なかった

種目選択の絞り込みリストが `{!(search.trim() && !findExercise(search.trim())) && (...)}` で
出し分けられており、**検索語が種目名と完全一致(またはエイリアス一致)でない限りリストが出ず、
「カスタム種目として追加」パネルに丸ごと切り替わっていた**。日本語で「ベンチ」と打っても
候補が 0 件だったので Phase 1 で入った問題ではないが、この経路では `exMatches()` が
一度も呼ばれず、英語で "bench" と打っても候補が出ないため、多言語化の意味が無くなる。

**候補リストは常に出し、カスタム追加パネルはその下に並べる**ように変えた。排他にしなかったのは、
既存種目と部分一致する名前(「カール」など)で新しくカスタム種目を作りたい場合を潰さないため。
同じ出し分けが「種目と種目の間に挿入」パネルにもあったので、そちらも同様に直している。
種目差し替えと種目設定の検索には元からこのゲートが無く、変更していない。
